# Технический план: Каталог музыкальных альбомов

Родитель: [spec.md](spec.md)
Модель данных: [data-model.md](data-model.md)
Контракт API: [contracts/openapi.yaml](contracts/openapi.yaml)
Задачи: [tasks.md](tasks.md)

## 1. Архитектура

Классическое разделение SPA + REST API:

```
┌─────────────────┐        HTTP/JSON, /api/*        ┌──────────────────────┐
│  Vue 3 SPA       │ ───────────────────────────────▶│  Django + DRF        │
│  (Vite, Pinia)   │◀─────────────────────────────── │  (ViewSets, filters) │
└─────────────────┘                                   └──────────┬───────────┘
                                                                   │ ORM
                                                          ┌────────▼────────┐
                                                          │   PostgreSQL    │
                                                          └─────────────────┘
```

Vite dev-сервер проксирует `/api` на Django в режиме разработки (см. `frontend/vite.config.ts`),
поэтому фронтенд всегда обращается к относительному пути `/api/...` — не нужно переключать
`baseURL` между локальной разработкой и продакшн-сборкой.

## 2. Backend

- **Django 6.1 + DRF 3.18**, приложение `catalog` в проекте `config`.
- Настройки разбиты на `config/settings/{base,dev,prod}.py` — `base.py` содержит общее,
  `dev.py` включает `DEBUG=True` и SQLite-фолбэк (`DATABASE_URL` не задан), `prod`/Docker-конфигурация
  через `DATABASE_URL` (Postgres) и `django-environ`.
- **Модели** — источник истины бизнес-правил (см. `data-model.md`). Ограничения выражены через
  `UniqueConstraint` на уровне БД, а не только через `clean()`/сериализаторы — согласно
  принципу конституции №2.
- **API** — `ModelViewSet` для `Artist`, `Album`, `Song` + вложенные `@action` на `AlbumViewSet`
  для управления треками (`tracks`, `tracks/{id}`, `tracks/reorder`), т.к. трек — не
  самостоятельный ресурс верхнего уровня, а часть агрегата «альбом».
- **Сериализаторы** разделены на List/Detail там, где вложенные данные дорогие (Album), чтобы
  список не тянул полный треклист. Все list-эндпоинты используют `select_related`/
  `prefetch_related` — отсутствие N+1 закрепляется тестом.
- **Фильтрация** — `django-filter` (структурные фильтры: `artist`, `year`, `year_min/max`) +
  DRF `SearchFilter` (свободный текст) + `OrderingFilter`.
- **Документация API** — `drf-spectacular`, автогенерируемая OpenAPI-схема экспортируется в
  `contracts/openapi.yaml` и коммитится как контракт (сверяется вручную при изменении API).
- **Обработка ошибок** — кастомный `EXCEPTION_HANDLER`, приводящий `IntegrityError`/`ValidationError`
  /`ProtectedError` к единому JSON-формату с корректным HTTP-статусом (400/409).

## 3. Frontend

- **Vue 3** (`<script setup>`, Composition API, TypeScript), **Vite**, **Pinia** для состояния,
  **Vue Router** для навигации, **axios** для HTTP, **vuedraggable** (обёртка над SortableJS)
  для drag&drop треклиста.
- Слой `src/api/*` — единственное место, знающее про HTTP и эндпоинты; возвращает типизированные
  DTO (`src/types/index.ts`, зеркалящие сериализаторы DRF).
- `src/stores/*` (Pinia) — хранят состояние списков/фильтров/пагинации, вызывают `src/api/*`,
  не содержат HTTP-деталей. Компоненты обращаются только к сторам.
- Состояние фильтров альбомов синхронизируется с query-параметрами URL через `vue-router`
  (`router.replace` при изменении фильтра) — обеспечивает шарибл-ссылки без доп. библиотек.
- Переупорядочивание треков: локальное оптимистичное обновление порядка в сторе сразу после
  drag-события, затем `PATCH .../reorder`; при ошибке — откат к серверному состоянию и toast
  с сообщением об ошибке.
- Никакого UI-фреймворка (Vuetify/Element) — простой собственный CSS с токенами
  (`styles/tokens.css`: цвета, отступы, радиусы), чтобы результат был компактным и предсказуемым
  для ревью, без magic-классов стороннего фреймворка.

## 4. Данные и целостность

См. [data-model.md](data-model.md). Ключевое архитектурное решение: `AlbumTrack` — явная
промежуточная модель (`through`), а не голый `ManyToManyField`, потому что связь несёт
собственный атрибут (`position`) и собственные ограничения целостности.

## 5. Тестирование

- **Backend**: `pytest-django` + `factory-boy`. Тесты моделей проверяют все ограничения БД
  (unique constraints, PROTECT) напрямую через `IntegrityError`/`ProtectedError`. Тесты API
  проверяют сценарии из критериев приёмки (AC-1…AC-7) через `APIClient`.
- **Frontend**: `Vitest` + `@vue/test-utils`, HTTP замокан на уровне `src/api/*` (никаких
  реальных сетевых вызовов в юнит-тестах).
- **CI**: backend-тесты гоняются против настоящего Postgres-сервиса в GitHub Actions (не SQLite),
  чтобы `Deferrable`-констрейнты и реальное поведение БД проверялись в CI так же, как в проде.

## 6. Инфраструктура и запуск

- `docker compose up` — три сервиса (`db`, `backend`, `frontend`), backend ждёт готовности БД
  (`healthcheck`), сам применяет миграции и наполняет демоданными при первом запуске
  (`seed_demo --if-empty`).
- Ручной запуск без Docker — backend на SQLite (`DJANGO_SETTINGS_MODULE=config.settings.dev`),
  frontend через `npm run dev`; описано в README как альтернативный путь для быстрой проверки.

## 7. Явно отклонённые альтернативы

- **`Song.album = ForeignKey(Album)` вместо M2M-through** — отклонено: прямо противоречит
  требованию «песня может входить в разные альбомы» (FR-05); пришлось бы дублировать записи
  песни, теряя смысл сущности «песня».
- **GraphQL вместо REST** — отклонено: DRF+REST — более стандартный и быстрее проверяемый
  ревьюером выбор для вакансии Django/Vue; GraphQL добавил бы объём без пользы для оценки.
- **Vuex вместо Pinia** — отклонено: Pinia — официально рекомендуемое решение для Vue 3,
  меньше boilerplate, лучше поддержка TypeScript.
