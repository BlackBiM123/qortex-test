# Конституция проекта: Каталог музыкальных альбомов

Этот документ фиксирует принципы, которым подчиняются все решения по спецификации, архитектуре и коду
в этом репозитории. Он не описывает функциональность — она в `spec.md`. Здесь — правила игры.

## 1. Spec-Driven Development

Ни одна строка кода не пишется раньше, чем зафиксировано **что** и **зачем** она реализует.
Порядок артефактов обязателен и неизменен:

1. `constitution.md` (этот файл) — принципы.
2. `spec.md` — требования: пользовательские сценарии, функциональные требования (FR-xx),
   критерии приёмки, явные Non-Goals.
3. `plan.md` — техническое решение: архитектура, границы слоёв, обоснование выбора технологий.
4. `data-model.md` — сущности, инварианты, ограничения БД.
5. `contracts/openapi.yaml` — контракт API, фиксируемый до и проверяемый после реализации.
6. `tasks.md` — атомарные задачи T-xx, каждая трассируется на конкретный FR-xx.

Каждый коммит реализации ссылается на номер задачи из `tasks.md`. Если в процессе кодирования
обнаруживается, что требование сформулировано неверно или неполно — сначала правится `spec.md`,
и только потом код.

## 2. Источник истины о данных

Модель предметной области (`data-model.md`) — это контракт, а не следствие удобной реализации.
Ключевой инвариант предметной области — переиспользуемость песни между альбомами с разными
порядковыми номерами — обязателен на уровне схемы БД (constraints), а не только на уровне
валидации в коде приложения. Если ограничение можно выразить в БД — оно выражается в БД.

## 3. Разделение слоёв

- Backend не знает о представлении данных на фронтенде; контракт — только через `contracts/openapi.yaml`.
- Frontend не обращается к API напрямую из компонентов — только через `src/api/*` → `src/stores/*` → компонент.
- Бизнес-правила (уникальность позиции, защита от удаления используемой песни) живут в моделях/сериализаторах
  Django, а не дублируются на фронтенде. Фронтенд может делать оптимистичные UI-проверки, но не является
  источником истины.

## 4. Определение готовности (Definition of Done)

Функциональность считается завершённой, когда одновременно выполнено:

- Есть автоматический тест, который ловит регрессию (backend — pytest, frontend — Vitest).
- Код проходит линтеры (`ruff`, `eslint`, `vue-tsc`) без подавления предупреждений.
- Поведение проверено вручную через запущенное приложение (Docker Compose), не только через тесты.
- Соответствующий пункт `tasks.md` отмечен выполненным со ссылкой на коммит.

## 5. Минимализм

Не добавляется функциональность, не отражённая в `spec.md`. Если решение допускает простой и
чуть более сложный вариант при равной надёжности — выбирается простой. Абстракции вводятся не
раньше, чем появляется второй конкретный случай использования.

## 6. Воспроизводимость

Любой человек должен суметь запустить проект локально одной командой (`docker compose up`) без
дополнительной настройки окружения, кроме копирования `.env.example` → `.env`. Все зависимости и
их версии — зафиксированы (lock-файлы коммитятся).
